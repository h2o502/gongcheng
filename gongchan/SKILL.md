# 工产 (gongchan) — 从需求澄清到产品设计的完整流程

## 核心定位

工产是**从需求澄清到产品设计的完整工作流框架**。它解决的核心问题是：从"对业务一无所知"到"进入开发环节"之间，需要经历哪些阶段、每步做什么、产出什么、检查什么。

工产是**产品经理思维**——关注产品范围、业务流程、数据设计、界面设计。它不是老板思维，不涉及商业运营层面的问题（那是 gongwen 的范围）。

工产**优先接收 gongxu（工需）的产出**作为输入：

- 必读：`docs/gongxu/GX-YYYYMMDD-XXX/03_needs.md`（工需清单）
- 必读：`docs/gongxu/GX-YYYYMMDD-XXX/02_standard_v1.md`（工需标准 v1.0）
- 参考：`docs/gongxu/GX-YYYYMMDD-XXX/05_proposal.md`（工需建议书）

如没有 gongxu 产出，工产会先用内置的**快速需求澄清**（gongxu 快速模式）补齐工需清单和标准，再进入设计阶段。

工产不是一次性脚本，而是**循环迭代的工作流**。架构在细节决策后反刍打磨，一致性检查反复回归会议纪要和工需清单，直到设计阶段自闭环无缺陷。

## 工产 vs 工问

| 维度 | 工问 (gongwen) | 工产 (gongchan) |
|------|---------------|----------------|
| **思维层级** | 老板思维 | 产品经理思维 |
| **覆盖范围** | 商业运营 + 产品 + 技术方案 | 纯软件产品设计 |
| **关注点** | 目标/干系人/实体/决策/约束/商业模式 | 流程/字段/状态机/数据结构/界面 |
| **输入** | 模糊的口述想法或半成品方案 | 已经过审问的明确需求（或直接开始） |
| **输出** | 方案底稿 (Proposal Draft) | 完整产品设计文档 + 界面设计稿 |

> 如果用户已经跑过 gongxu，工产可以直接从阶段一开始（demon + 分项开会），工需清单和标准作为阶段二的输入。如只有 gongwen 方案底稿，先跑 gongxu 快速模式补齐工需清单。

## 确认门禁规范

每个阶段结束时，AI 必须主动检查冲突和不确定的地方，按以下格式向用户汇报：

1. **汇报状态**：当前阶段完成了什么
2. **列出发现**：冲突/缺陷/不确定的地方（用表格，每条后面标注严重程度）
3. **给出建议**：每个发现问题给出推荐方案
4. **等待确认**：明确问"是否继续？"或"选哪个方案？"

**禁止行为**：
- 不要跳过确认直接进入下一步
- 不要在用户未确认时自行修改设计
- 不要把多个决策混在一起问——一次只问一个关键决策

## 阶段一：建立沟通阶段

> 通过 demon → 分项开会 → 语音转录三步，自然对齐各方的颗粒度。

### 前置步骤：读取 gongxu 产出（如存在）

进入阶段一之前，AI 必须检查是否存在 gongxu 产出：

```
docs/gongxu/GX-YYYYMMDD-XXX/
├── 02_standard_v1.md      # 工需标准 v1.0
├── 03_needs.md            # 工需清单
└── 05_proposal.md         # 工需建议书
```

**如果存在**：
- 读取并理解《工需标准》和《工需清单》
- 在后续阶段二中逐项对照
- demon 必须体现 P0 工需的核心闭环

**如果不存在**：
- 执行内置**快速需求澄清**（gongxu 快速模式）
- 至少输出：《任务信号卡》《工需标准 v1.0》《工需清单》
- 存入 `docs/gongxu/GX-YYYYMMDD-XXX/`

### 步骤 1：望文生义做 Demon

**做什么**：拿到产品名称或简短描述后，立即做一个粗略的 demon（原型/草案），不追求准确，只追求快速可视化。

**为什么**：demon 是沟通的起点。有一个东西摆出来，各方才能说"这里不对""那里要改"。空对空讨论效率极低。

**产出**：
- 粗略的产品框架图（模块划分）
- 关键页面草图（HTML/线框图）
- demon 代码（可运行的最小原型）

**注意**：demon 的代码权重约 10%，仅作参考。后续设计不绑定 demon 的实现。

**检查点**：
- [ ] demon 能跑起来吗？核心业务流程能走通吗（哪怕靠硬编码）？
- [ ] 能让非技术人员看懂"这个产品大概做什么"吗？

---

### 步骤 2：分项开会做会议记录

**做什么**：和使用各方（业务方、操作人员、管理者）分别沟通开会，做详细的会议记录。

**关键原则**：
- **分项开会**：不同部门/角色分开开会，不要一锅端
- **按业务流程顺序开会**：先开上游部门（如市场→销售→合同→财务），再开下游部门
- **详细记录业务实际场景**：不是听他们说要什么功能，而是记录他们实际怎么工作的
- **工作流程优先**：先搞清楚业务流程，再谈系统功能
- **字段和规则要抠细节**：状态枚举、计算规则、边界条件、异常处理
- **断点必须记录**：当前流程中哪里断了、谁在手动补、怎么补的

**产出**：
- 每个部门/角色一份独立的会议纪要
- 按业务流程顺序排列（不是按开会时间）
- 包含：业务流程、字段细节、状态枚举、业务规则、痛点、外部系统依赖

**文件结构规范**：
```
docs/meetingrecord/
├── 01_部门A_日期.md       # 按业务流程顺序编号
├── 02_部门B_日期.md
├── ...
└── _raw/                  # 原始转写和帧分析
    ├── xxx_frames.txt
    └── xxx_transcript.txt
```

**检查点**：
- [ ] 每个部门的业务流程是否完整记录？
- [ ] 字段细节、状态枚举、计算规则是否遗漏？
- [ ] 外部系统依赖是否标注？
- [ ] 断点、异常、需要人工判断的节点是否记录？

---

### 步骤 3：语音转录和视频解析

**做什么**：将会议录音/录像进行语音转录和视频解析，越详细越好，按模块拆分。

**关键原则**：
- **越详细越好**：宁可多记不可漏记。一句话可能包含一个关键业务规则
- **按模块拆分**：转录完成后，按业务模块重新组织，不按时间顺序
- **保留原始材料**：原始转写和帧分析保存在 `_raw/` 目录
- **术语校准**：转录后校正关键业务术语（不是谐音错字）

**工具**：
- 语音转录：SenseVoice / DashScope
- 视频解析：video-parser skill
- 帧分析：提取关键帧 + OCR

**产出**：
- 完整的语音转写文本（`_raw/xxx_transcript.txt`）
- 视频帧分析（`_raw/xxx_frames.txt`）
- 按模块拆分整理后的会议纪要

**文件整理**（转录完成后立即做）：
- **按业务流程顺序编号**：01→02→03→...，不是按开会时间
- **合并同部门多次会议**：如账单部开了 2 次会，合并到一个文件
- **拆分混合会议**：如某次会议同时涉及两个部门，拆分成两个文件
- **预留未开会的空文件**：按业务流程顺序，已识别但尚未开会的部门预留空文件

**检查点**：
- [ ] 转录是否完整（无大段遗漏）？
- [ ] 关键业务术语是否准确？
- [ ] 是否按模块拆分整理？
- [ ] 文件编号是否按业务流程顺序连续？同部门多次会议是否合并？混合会议是否拆分？

## 阶段二：需求沟通和整理阶段

> 将会议纪要转化为产品设计。从模块设计 → 架构汇总 → 反刍打磨 → 用户规则校准。

### 步骤 4：每个模块单独整理产品设计

**做什么**：基于会议纪要和 gongxu 工需清单，为每个业务模块单独整理产品设计。

**关键原则**：

- **一个模块一份文档**：不要混在一起
- **以业务流程为主线**：设计跟着业务走，不是跟着技术对象走
- **闭环优先**：每个模块内部必须能形成完整闭环，不依赖外部系统
- **外部系统是适配器**：如果需要对接外部系统，设计为适配器，内部有兜底
- **对照工需清单**：每个模块设计文档开头必须列出"本模块覆盖的 P0/P1 工需"

**产出**：
- 每个模块的设计文档（职责、核心对象、状态机、业务规则、外部依赖、覆盖的工需）
- 模块间的接口定义
- 《工需覆盖对照表》：模块 → 承接的 P0/P1/P2 工需

**检查点**：
- [ ] 每个模块是否独立闭环？
- [ ] 外部系统依赖是否有兜底方案？
- [ ] 状态枚举是否完整？
- [ ] 业务规则是否与会议纪要一致？
- [ ] 每个 P0 工需是否都有模块承接？
- [ ] 是否有模块做了 P2 但漏了 P0？

---

### 步骤 5：汇总做整体架构设计

**做什么**：将各模块设计汇总，做整体架构设计。

**关键原则**：
- **分层架构**：平台基座层 + 业务域层（+ AI 是外挂，不是一层）
- **系统闭环为最高原则**：每个业务域内部必须有完整业务映射
- **模块间通过事件解耦**：业务域之间不直接调用，通过事件总线发布/订阅
- **主键回归业务**：每个实体的唯一识别方式由业务决定，不是一律自增 ID

**产出**：
- 架构总览文档（设计原则、大模块地图、决策记录）
- 模块设计文档（每个模块的职责、闭环规格、适配器映射、事件）
- 大模块关系图（PlantUML）
- 决策日志，格式如下：

| 决策 | 选项 | 选择 | 理由 | 日期 |
|------|------|------|------|------|
| AI 定位 | 1 系统部分 / 2 外挂工具 | 2 | 硬规则多，合规风险高，流程可脱离 AI 跑通 | 2026-07-27 |
| 房源唯一识别 | 邮编 / 邮编+门牌号 | 邮编+门牌号 | 英国邮编到~15 户，需门牌号到户 | 2026-07-28 |
| 客户唯一识别 | 邮箱 / 微信 / 系统 ID | 系统 ID+人工合并 | 任何字段都可能重复或缺省 | 2026-07-28 |
| ... | ... | ... | ... | ... |

**newdesign 文件结构规范**：
```
docs/newdesign/
├── 00_总览.md                    # 设计原则 + 模块地图 + 决策记录
├── 01_系统模块设计.md             # 每个模块的职责/闭环规格/适配器
├── 02_系统底座设计.md             # 鉴权/消息/流程/组织/事件等底座逻辑
├── 03_数据结构设计_平台基座层.md   # 底座数据表字段定义
├── 04_数据结构设计_业务域层.md     # 业务数据表字段定义
├── 05_外部系统字段映射检验.md      # 外部系统字段对照
├── 06_Monday字段完整映射.md        # 外部系统字段补全
├── 07_业务流程闭环设计.md          # 正逆向流程 + 事件清单 + 核心入参
├── diagrams/                     # 架构图/流程图/ER图

│   └── ...

**非标准编号的参考文件**（如用户提供的原始需求文档、其他 session 产出的设计稿）：
- 移入 `reference/` 子目录
- 或在文件名前加 `REF_` 前缀
- 避免与主设计文档编号混淆

**检查点**：
- [ ] 架构分层是否清晰？
- [ ] 模块间关系是否明确（调用/事件/适配器）？
- [ ] 决策记录是否完整（为什么选 A 不选 B）？
- [ ] 是否与 demon 做了对比？

### 步骤 6：反复反刍打磨系统底座

**做什么**：在细节决策和修改后，反复反刍整体架构设计，打磨系统底座。

**关键原则**：
- **细节决策会反向影响架构**：一个字段的缺失可能暴露一个流程的断点
- **反刍不是重写**：是在已有架构上找缺陷、补漏洞、修矛盾
- **系统底座是打磨重点**：鉴权、消息中心、流程引擎、组织架构、数据结构、事件总线

**反刍维度**：
1. **业务流程闭环完整性**：每个流程能否在系统内跑通（正向+逆向）
2. **跨域联动是否有断点**：事件总线的事件是否覆盖所有跨域场景
3. **数据结构是否有遗漏**：对照会议纪要的字段和规则
4. **状态机是否完整**：各业务对象的状态枚举是否覆盖所有场景
5. **适配器闭环是否真能兜底**：无 API 的外部系统降级方案是否可行
6. **文档间是否自洽**：各文档的表名、枚举、事件名称是否一致

**缺陷分级**：
| 等级 | 定义 | 示例 |
|------|------|------|
| 🔴 闭环缺陷 | 业务流程跑不通 | 退租流程缺 state 枚举、缺对账单表 |
| 🟡 设计缺陷 | 能跑但设计有隐患 | 命名不一致、事件缺漏 |
| 🟢 完善建议 | 增强项，不阻塞 | 死信队列、配置管理表 |

**确认门禁**：反刍完成后，AI 必须主动检查冲突和不确定的地方，向用户汇报缺陷清单，确认后再进入下一步。

**产出**：
- 反刍报告（缺陷清单 + 严重程度分级 + 修复方案）
- 修正后的架构文档

**检查点**：
- [ ] 正向流程是否闭环？
- [ ] 逆向流程是否闭环？
- [ ] 正逆向是否衔接？
- [ ] 异常分支是否回归主流程？
- [ ] 文档间是否有矛盾？

---

### 步骤 7：工需标准校准

**做什么**：对照 gongxu 的《工需标准 v1.0》和《工需清单》，校准设计方向。如无 gongxu 产出，则参考用户自己整理的需求和规则完成校准。

**关键原则**：
- **工需标准是验收基线**：设计必须满足工需清单中的 P0 项，P1 项尽量满足，P2 项可选
- **用户的需求文档是正典**：设计不能违背用户的明确要求
- **用户的规则是硬约束**：如"先有人工闭环再 AI""断点交给人"等
- **冲突时追问**：AI 必须主动检查设计是否与工需标准/用户规则冲突，冲突时不要自作主张改设计，先向用户说明冲突并追问

**确认门禁**：检查完成后，AI 必须向用户汇报对照结果，确认无冲突后再进入阶段三。

**产出**：
- 《工需覆盖对照表》（最终版）
- 《设计偏差清单》（如有）
- 冲突清单（如有）

**检查点**：
- [ ] 所有 P0 工需是否都在设计中有对应实现？
- [ ] 设计是否满足用户的硬约束？
- [ ] 用户的需求是否全部覆盖？
- [ ] 有没有设计偏离用户意图或工需标准的地方？

---

## 阶段三：详细设计阶段

阶段三分为三个子阶段，依次执行：

```
3A 底层架构设计（只看整体）→ 3B 后端相关设计 → 3C 前端相关设计
```

### 3A：底层架构设计 · 只看整体（步骤 8-10）

> 3A 和阶段二构成迭代循环：反刍→检查→发现新缺陷→再反刍，直到无缺陷为止。

### 步骤 8：回归会议纪要与工需清单做一致性检查

**做什么**：设计完成后，再次回归会议纪要、工需清单和用户规则，做三个维度的一致性检查。

#### 8a. 业务一致性（设计 vs 会议纪要）

**关键原则**：会议纪要是业务真相的来源，设计必须与之一致。逐条核对每个业务流程、字段、规则、状态枚举都要在设计中找到对应。

**产出**：
- 一致性检查报告（会议纪要条目 → 设计文档位置 → 是否覆盖）
- 缺口清单

#### 8b. 工需一致性（设计 vs 工需清单）

**关键原则**：gongxu 的《工需清单》是验收基线，设计必须覆盖所有 P0 项。

**产出**：
- 工需覆盖检查报告（P0/P1/P2 工需 → 设计实现位置 → 是否覆盖）
- 未覆盖清单（如有，必须回退到阶段二修正或回退到 gongxu 更新清单）

**检查点**：
- [ ] 每个 P0 工需是否都有明确的设计实现？
- [ ] P0 实现是否完整（不是只提到名词，而是有流程/字段/页面支撑）？
- [ ] 是否有设计范围超出工需清单且未与用户确认？

#### 8c. 文档自洽性（设计文档之间）

**检查维度**：
| 维度 | 检查内容 |
|------|---------|
| 表名一致性 | 各文档中同一张表是否用同一名称 |
| 枚举一致性 | 同一枚举在不同文档中是否一致（大小写、格式）|
| 事件一致性 | 流程设计用到的事件是否在事件清单中有定义 |
| 节点类型一致性 | 底座设计的节点类型和数据结构的 node_type 枚举是否一致 |
| 适配器清单一致性 | 模块设计的适配器列表和数据结构的 adapter_config 是否一致 |
| 导航一致性 | 各文档末尾的导航链接是否覆盖全部文档 |

**确认门禁**：AI 必须主动检查上述两个维度，发现不一致向用户汇报，确认修正方案后再执行。

**产出**：
- 业务一致性报告 + 文档自洽性报告
- 修正后的文档

**检查点**：
- [ ] 每个部门的业务流程/字段/规则/状态枚举是否在设计中有对应？
- [ ] 所有表名、枚举、事件、节点类型、适配器清单是否一致？
- [ ] 所有文档导航是否完整？

---

### 步骤 9：外部系统对接一致性查漏补缺

**做什么**：对外部系统和现有系统对接做一致性查漏补缺。

**关键原则**：
- **字段映射**：外部系统的每个字段都要在我们系统里找到对应位置
- **不需要完整复刻**：只映射使用到的字段，不用的字段不管
- **对接路径可切换**：如 Rightmove/Zoopla 可直连也可通过 1090 中转
- **闭环兜底**：外部系统不可用时有降级方案

**产出**：
- 外部系统字段映射检验文档
- 对接路径设计方案
- 缺失字段清单

**检查点**：
- [ ] 每个外部系统的字段是否都有映射？
- [ ] 对接路径是否可切换？
- [ ] 降级方案是否可行？
- [ ] 是否有字段丢失？

---

### 步骤 10：循环检查业务流程闭环

**做什么**：循环检查业务流程闭环——正向、逆向、异常分支，以及 P0 工需覆盖度。这是底层架构设计的"终极验收"。

**关键原则**：
- **正向闭环**：从起点到终点能否跑通（如：商机→定房→签约→入住→居住）
- **逆向闭环**：退租/退款/取消等逆向流程能否跑通
- **正逆向衔接**：逆向终点是否回到正向起点（如：退租→房源回空置→重新招租）
- **异常回归**：异常分支是否回归主流程（如：催收→退租→押金扣除）
- **并行汇合**：多并行子流程必须有明确的汇合点
- **P0 工需覆盖度**：每个 P0 工需都必须在闭环矩阵中找到对应流程节点

**停止条件**：循环检查直到无新缺陷。这里的"无缺陷"指设计阶段的自闭环无缺陷，不代表实际运行时不出问题。

**确认门禁**：每轮检查后，AI 向用户汇报闭环状态，确认后再决定是否继续循环。

**产出**：
- 闭环验证报告（检查结果：每个流程节点是否闭环、缺口在哪）
- 闭环检验矩阵（每个流程节点 → 入参 → 出参 → 事件 → 是否闭环）
- P0 工需覆盖度矩阵（P0 工需 → 覆盖的流程节点/模块）

**注意**：步骤 10 产出的是验证报告（检查结果），不是流程设计文档本身。流程设计文档由步骤 12 产出。

**检查点**：
- [ ] 正向流程是否闭环？
- [ ] 逆向流程是否闭环？
- [ ] 正逆向是否衔接？
- [ ] 异常分支是否回归？
- [ ] 并行子流程是否有汇合点？
- [ ] 每个 P0 工需是否都有流程节点覆盖？
- [ ] 发现的缺口是因为设计遗漏还是工需清单遗漏？（后者回退 gongxu）

> **此步骤可能发现新的缺陷，必须循环回到阶段二步骤 6 反刍架构。循环直到无缺陷为止。**

---

### 3B：后端相关设计（步骤 11-12）

> **门禁**：3A 全部通过后，才能进入 3B。底层架构未定就做数据结构，会导致反复返工。

### 步骤 11：字段细节整理和数据结构设计

**做什么**：整理字段细节，设计完整数据结构，根据业务确定每个表的主键。

**关键原则**：
- **主键回归业务**：
  - 能业务唯一识别的（如房源=邮编+门牌号）用业务键
  - 不能业务唯一识别的（如客户=只能 ID + 人工合并）用系统 ID
  - 系统生成的（如合同号/账单号）用编号中心统一生成
- **实体与登录分离**：客户/供应商/员工都是实体，但只有员工登录系统
- **跨域不 join**：业务域之间通过事件联动，不直接跨表 join
- **命名统一**：表名前缀按模块分（如 `user_*` / `message_*` / `property` / `lease`）
- **不照搬外部系统**：外部系统是单表不是系统，数据结构要按业务逻辑拆表，不要照搬外部系统字段

**确认门禁**：数据结构设计完成后，AI 必须向用户汇报每张表的主键选择理由，确认后再进入下一步。

**产出**：
- 平台基座层数据结构文档（鉴权/消息/流程/组织/事件/编号/适配器等表）
- 业务域层数据结构文档（房源/CRM/合同/财务/账单/工单等表）
- 每张表的字段定义（字段名/类型/约束/说明）
- 枚举值清单
- 《字段 ↔ 工需映射表》：核心字段 → 服务的 P0/P1 工需

**检查点**：
- [ ] 每个表的主键是否由业务决定？
- [ ] 实体与登录是否分离？
- [ ] 字段是否覆盖会议纪要的所有细节？
- [ ] 外部系统字段是否都有对应位置？
- [ ] 命名是否统一？
- [ ] 每个 P0 工需所需的核心字段是否都已定义？
- [ ] 是否有字段没有对应工需支撑（防止过度设计）？

---

### 步骤 12：工作流程梳理和核心入参

**做什么**：梳理完整工作流程，确定主要系统和流程之间的核心入参。

**关键原则**：
- **流程节点类型**：start / end / human_task / decision / timer / wait_event / notification / sub_process / parallel
- **任务可分配给人或 AI**：AI 不是流程节点类型，而是 human_task 的执行者之一
- **并行子流程有汇合点**：多条并行分支必须有明确的汇合条件
- **核心入参明确**：每个流程的输入参数、输出参数、事件发布/订阅要定义清楚

**产出**：
- 业务流程闭环设计文档（正向+逆向+异常流程图）
- 核心入参清单（每个流程的输入/输出/事件）
- 事件清单（所有跨域事件，含发布域和订阅方）

**检查点**：
- [ ] 流程节点类型是否完整？
- [ ] 并行子流程是否有汇合点？
- [ ] 核心入参是否明确定义？
- [ ] 事件清单是否与数据结构中的事件一致？

---

### 3C：前端相关设计（步骤 13-17）

> **门禁**：3B 全部通过后，才能进入 3C。数据结构未定就做界面，会导致反复返工。

### 步骤 13：进入界面设计环节

**做什么**：数据结构和流程设计完成后，制定界面设计计划。

**前提条件**：
- [ ] 数据结构设计已完成
- [ ] 业务流程闭环已验证
- [ ] 一致性检查已通过
- [ ] 外部系统字段映射已完成

**产出**：界面设计计划（哪些页面、什么顺序）

---

### 步骤 14：HTML 静态页多种结构尝试

**做什么**：用 HTML 静态页做多种结构尝试，不急于定稿。

**关键原则**：
- **多种方案并行**：同一页面做 2-3 种布局方案，对比后选最优
- **静态优先**：先用纯 HTML/CSS，不写 JS 逻辑
- **核心流程优先**：先做核心业务流程涉及的页面
- **不过度设计**：只做结构和布局，不做视觉细节

**产出**：多套 HTML 静态页方案

**检查点**：
- [ ] 是否做了多种结构尝试？
- [ ] 核心业务流程的页面是否覆盖？
- [ ] 页面结构是否匹配数据结构？

---

### 步骤 15：UI 风格与视觉规范

**做什么**：确认 UI 风格，做 UI 主题色规则设计、字体大小和梯度设计、间隔和通用组件视觉设计。

**风格选择**（可选其一或混合）：
- Windows / Fluent Design
- 苹果 / Human Interface Guidelines
- 现成组件库（Ant Design / Element Plus / Material UI）

**设计内容**：
- **主题色**：主色/辅色/语义色（成功/警告/错误/信息），支持多主题（如 light/warm/dark）
- **字体梯度**：标题层级（H1-H6）/正文/辅助文本/按钮文字的字号和字重
- **间隔系统**：基准间距单位（如 4px），页面/卡片/组件/元素各级间距
- **通用组件**：按钮/输入框/表格/卡片/弹窗/标签/徽章的视觉规范
- **设计令牌**：用 CSS 变量定义所有设计值

**如果有跨项目复用需求**：提取设计令牌到共享层（如 `tokens.css`），用 CSS 变量定义，支持多主题切换。所有 APP 通过 `<link>` 引用共享层，禁止硬编码色值/间距/圆角。

**产出**：
- `tokens.css`（设计令牌）
- UI 规范文档
- 组件视觉示例

**检查点**：
- [ ] 主题色是否完整（主色/辅色/语义色/多主题）？
- [ ] 字体梯度是否覆盖所有层级？
- [ ] 间隔是否统一使用基准单位？
- [ ] 通用组件是否都有视觉规范？
- [ ] 设计令牌是否用 CSS 变量？

---

### 步骤 16：主页面串联与交互设计

**做什么**：基于步骤 14 选定的结构方案和步骤 15 的视觉规范，完成每一个系统的主页面 HTML 静态页串联，确定核心业务流程的页面关系和核心交互设计。

**注意**：步骤 16 不重新做结构或视觉，只做串联和交互。结构和视觉在步骤 14-15 已确定。

**关键原则**：
- **页面关系图**：画出页面之间的跳转关系（用 PlantUML/流程图）
- **核心交互**：每个关键操作的交互流程要明确定义（点击→反馈→跳转→状态更新）
- **串联验证**：沿着核心业务流程走一遍，确认页面串联无断点
- **响应式**：PC/移动端适配方案

**产出**：
- 全部系统主页面的 HTML 静态页
- 页面关系图
- 交互设计说明

**检查点**：
- [ ] 每个系统的主页面是否完成？
- [ ] 页面串联是否覆盖核心业务流程？
- [ ] 交互设计是否明确定义？
- [ ] PC/移动端是否适配？

---

### 步骤 17：根据设计 Demon 完整设计

**做什么**：根据之前的设计 demon 和所有设计文档，进行完整设计——把所有静态页、交互、数据结构、流程整合成完整的设计稿。

**确认门禁**：完整设计完成后，AI 向用户汇报，确认所有页面与数据结构/流程设计一致，确认可以交给开发。

**产出**：
- 完整的页面设计稿（全部页面 + 交互 + 状态）
- 设计文档与页面的对照表
- 开发交接清单

**检查点**：
- [ ] 所有页面是否与数据结构对应？
- [ ] 所有交互是否与流程设计一致？
- [ ] 设计是否满足所有用户需求？
- [ ] 是否可以交给开发？

## 回退机制

工产在设计过程中，遇到以下情况必须回退到 gongxu：

| 回退场景 | 回退动作 | 更新产物 |
|---------|---------|---------|
| 发现原始需求有歧义 | 回到 gongxu Step 2 追问 | 追问清单、工需标准 |
| 某个 P0 工需无法在当前设计下落地 | 回到 gongxu Step 5/6 | 工需清单、自生需求补充 |
| 用户提出新需求，需要重新评估优先级 | 回到 gongxu Step 5 | 工需清单（P0/P1/P2 重排） |
| 闭环验证时发现关键缺口，判断为需求遗漏 | 回到 gongxu Step 6 | 自生需求补充、工需清单 |
| 设计范围与工需标准冲突 | 回到 gongxu Step 4 校准 | 工需标准 v1.0 |

**回退原则**：
- 不是重跑整个 gongxu，只更新受影响的部分
- 更新后的《工需标准》和《工需清单》必须重新进入工产阶段二/三检查
- 所有回退和重新进入都要记录到决策日志

## 使用场景

### 场景一：从零设计新产品

```
用户："我要做一个房产管理系统"

## 核心原则速查

| 原则 | 说明 |
|------|------|
| **系统闭环** | 每个业务域内部必须完整闭环，不依赖外部系统 |
| **AI 是外挂** | AI 通过 MCP/接口挂载，不是系统的一层；系统不知也不关心是人还是 AI 在操作 |
| **主键回归业务** | 每个实体的唯一识别方式由业务决定 |
| **事件解耦** | 业务域之间通过事件总线联动，不直接调用 |
| **先闭环后细节** | 先大逻辑跑通，再抠字段细节 |
| **循环反刍** | 架构设计不是一次成型，细节决策后要反刍整体 |
| **回归源头** | 设计完成后回归会议纪要做一致性检查 |
| **实体与登录分离** | 客户/供应商/员工都是实体，但只有员工登录 |
| **门禁准入** | 每个阶段有明确检查点，全部通过才能进入下一阶段 |
| **AI 主动确认** | 关键节点 AI 必须主动检查冲突和不确定的地方，向用户汇报并确认 |
| **决策日志** | 每个关键决策记录选项/选择/理由/日期 |
